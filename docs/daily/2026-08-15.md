## 測るときの作法（今日ひっくり返ったもの）

1. **設定ファイルの「有効な設定」は、コメントを除去して構造として読む。**
   この艦隊は「撤去の理由をコメントで残す」作法を持つので、**作法そのものが `grep` の精度を下げる**。
   ⚠️ **この外れ方は安全側に見える**（射程が過大に出るので「慎重に見積もった」ように読める）＝気づきにくい。
2. **道具の目的関数を疑う。** `npm audit fix` は「advisory を消す」ことだけを目的にしていて、
   **依存グラフを保つことは目的に入っていない**。⇒ **事故った本人を疑う前に、本人が使った道具を疑う。**
3. **3艦で成功した型が、4艦目で事故を起こす。成功回数は安全性の証拠にならない。**
4. **「同じファイルを配る」と「同じ検査を受ける」は別。** 受け手の CI の射程は艦ごとに違う。
5. **「main が赤い」は run の結論だけでは読めない。** 故障注入の赤と実欠陥の赤がある。
6. **安全弁は GO が出ても外さない。** hub の GO は「足してよい」であって「前提を確かめなくてよい」ではない。
7. **数字を受け取ったら「どの木で測ったか」を確認する。** 本日 hub の数字は3回それが抜けた
   （grep 由来の射程／lockfile を grep で未検出／`main` ではなく PR ブランチの木で測った 0件）。
   判例44⑥（測った環境を一行添える）は、**出す側が守れていないことがある**という前提で受け取る。
8. **照会は、聞かれた側の持ち物を点検させる。** 推測が外れていても価値は出る（本日2回・§7）。
