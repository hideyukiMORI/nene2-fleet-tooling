# `docs/ci/` — フリートへ配る CI の原本

ここに置いた yml は **配布物の原本**であって、**この repo では走らない**。
`.github/workflows/` に置くと GitHub が実行するが、**fleet-tooling は PHP を持たない**
〔`composer.json` 無し・実測〕ので、`composer audit` は原理的に緑にできない。

🔑 **走らないものを緑と数えない**（hub 裁定 2026-08-27 (a)+(b)）。
**原本の家は自艦（版管理のため）／動作の証明は適用1号の艦で取る。**

## `weekly-audit.yml`

**PHP 依存の週次再検査**（施主決定 2026-08-22 (c)・板 L99・fleet #502）。

**受け手 = 7艦**: `clear` / `concierge` / `contact` / `deal` / `invoice` / `records` / `vault`

⚠️ **一斉配信はしない**（hub 了承）。**各艦が次に CI を触るときに同梱する。**

### 写すときに各艦で決める4点

| # | 何を | なぜ |
| --- | --- | --- |
| 1 | **cron の「分」** | NENE2 が `30 1 * * 1` で既に1艦2枠。**1時台25分以降・30分は避ける** |
| 2 | **`notify-failure` の `if`** | 🔴 **文字列を写さない。その artifact が「無人で走る」event を列挙する** |
| 3 | **`timeout-minutes`** | 🔴 **値ではなく手順を写す**（直近30 run の success 全数の**最大の10倍**） |
| 4 | `ISSUE_TITLE` の艦名 | 重複検出が題名の一致で効くため |

### 🔴 DoD — 陽性対照は **2段**。1回では足りない

**invoice が PR #767 で実証**（hub 経由で受領）:

| 回 | 通る経路 | `--limit 1000` は効くか |
| ---: | --- | --- |
| **1回目** | **Issue の新規作成**（既存が無いので `gh issue list` の結果は空） | ❌ **効かない** |
| **2回目** | **重複検出 → 既存 Issue にコメント** | ✅ **ここで効く** |

⇒ **1回で終える陽性対照は「Issue が立つ」ことしか確かめていない。**
**`--limit 1000` に直した意味は、2回目まで回さないと1バイトも検証されていない。**

🔑 **「対照が発火することを見た」の一段先。** 対照は発火している（Issue が立つ）。
**ただし発火したのは、直した経路ではない。**
⇒ **「対照が発火した」ではなく「対照が、直した経路を通って発火した」まで問う。**

**手順**:

1. `workflow_dispatch` を `simulate_failure=true` で叩く ⇒ **Issue が1本立つ**
2. 🔴 **もう一度叩く** ⇒ **新規作成されず、既存 Issue にコメントが付く**
3. テスト由来の Issue を**説明付きで閉じ**、**open 数が実験前と同数に戻る**ことを確認

⚠️ **陽性対照を回すと本物の Issue が1件立つ**（invoice 実測）。
⇒ 🔴 **適用先の艦に「テスト由来の Issue が1件立つ」と先に伝えること。**
🔑 **黙って立つと、それこそ「毎週重複を立てる装置」と見分けがつかない。**

### 既知の落とし穴

- 🔴 **`setup-php` は `COMPOSER_NO_AUDIT=1` を立てる**（#281・3艦で再現）。
  殺されるのは **install/update に付随する暗黙の audit** で、**明示的な `composer audit` は生きている。**
  ⇒ 「setup-php を使っているから audit は死んでいる」と読まない。**暗黙は死んでいるが明示は生きている。**
- 🔴 **写す先に `schedule` が無いのに `schedule` を条件へ写すと、simulate 以外で永久に発火しない**
  （vault の backend-ci がこの形・#379）。**条件は「持っている event」から導出する。**
- **PR 時の `composer audit` と週次は両方残す**（hub 裁定）。**目的が違う**——PR 即時検知と週次再検査。
  週次が要るのは **advisory が我々のコミットではなく向こう側の時計で公開される**から。
