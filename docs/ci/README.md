# `docs/ci/` — フリートへ配る CI の原本

ここに置いた yml は **配布物の原本**であって、**この repo では走らない**。
`.github/workflows/` に置くと GitHub が実行するが、**fleet-tooling は PHP を持たない**
〔`composer.json` 無し・実測〕ので、`composer audit` は原理的に緑にできない。

🔑 **走らないものを緑と数えない**（hub 裁定 2026-08-27 (a)+(b)）。
**原本の家は自艦（版管理のため）／動作の証明は適用1号の艦で取る。**

## `weekly-audit.yml`

**PHP 依存の週次再検査**（施主決定 2026-08-22 (c)・板 L99・fleet #502）。

**受け手 = 7艦**: `clear` / `concierge` / `contact` / `deal` / `invoice` / `records` / `vault`

⚠️ **一斉配信はしない**（hub 了承）。**各艦が次に CI を触るときに同梱する。**

### 🔴 写す手順（#512 — vault が適用1号で見つけた）

**`weekly-audit.yml` には「写しでも真であり続ける事実」しか書いていない。**
**配布のための指示・割当表・節番号つきの参照は、すべてこの README 側にある。**

🔑 **配布物のコメントは「原本での意味」と「写しでの意味」が違う。**
**「ここは原本なので」「上の 3」「◯◯に変えること」は原本でだけ正しく、写した瞬間に嘘になる。**

**実際に起きたこと**（`nene-vault#493`）: 中身は全部正しく vault 用になっていたのに、
cron の行のコメントだけが **「ここは原本なので未割当の 25 を置いてある」**と言っていた——**値は 40 なのに。**
⇒ **同じファイルの中で3つが矛盾した**（コメントの 25 ／ 実際の 40 ／ 冒頭の「原本はここ」）。

🔴 **次に読む人が「ここが原本」と信じると、上流へ返すべき修正をそこで止める。**
**配布物にとっては、値の誤りより「自分の身元の誤り」の方が遠くまで効く。**

⇒ **対策は「写すときに書き換える」ではなく「原本にその種のコメントを置かない」**（**写す回数だけ効く**ため）。

### 写すときに各艦で決める3点

| # | 何を | なぜ |
| --- | --- | --- |
| 1 | **cron の「分」** | NENE2 が `30 1 * * 1` で既に1艦2枠。**1時台25分以降・30分は避ける** |
| 2 | **`notify-failure` の `if`** | 🔴 **文字列を写さない。その artifact が「無人で走る」event を列挙する** |
| 3 | **`timeout-minutes`** | 🔴 **値ではなく手順を写す**（直近30 run の success 全数の**最大の10倍**） |
| 4 | ~~`ISSUE_TITLE` の艦名~~ | 🟢 **決める必要が無くなった** — `GITHUB_REPOSITORY` から**導出**する（#512・vault 提案）。**置換する場所が無いので置換漏れも起きない** |

### 🔴 なぜ「未置換を落とすガード」ではなく「導出」なのか（#512・vault の差し戻し）

一度は **`ISSUE_TITLE` が未置換なら `exit 1`** するガードを入れたが、**vault に差し戻された**:

| | 置換漏れが起きたとき |
| --- | --- |
| ガード無し | `🔴 <艦名>: …` という題の Issue が**立つ**。見た目は悪いが**失敗は表に出る** |
| **ガード有り** | notify が `exit 1` ⇒ **Issue が立たない。** run は赤だが、**その赤を見る人が居ないからこの装置が在る** |

🔴 **ガードは、無人失敗を可視化する装置を、無人失敗のときに黙らせる。**
🔑 **`--limit` の節が自分で書いている形と同じ**——「この仕掛けが守ろうとしているものを、最も必要なときに自分で壊す」。
**`--limit` は取りこぼして重複を立て、ガードは何も立てない。沈黙の方が悪い。**
⚠️ **発見も遅れる**——ガードは notify が走るときしか評価されないので、**最初の実失敗まで潜む。**

⇒ **導出に替えた。** 🔑 **「変えないと目立つ値にする」より一段上＝変える必要をなくす。**
（原本のコメントで採った「写すときに書き換える」→「そもそも置かない」と**同じ動き**。）

**`GITHUB_REPOSITORY` を使う理由**: Actions が**どの event でも必ず設定する既定環境変数**なので payload に依存しない。
⚠️ `github.event.repository.name` も `workflow_dispatch` では解決する（vault 実測・Issue #496）が、
**`schedule` の payload での解決は未計測**だったので採らなかった。

### 🔴 DoD — 陽性対照は **2段**。1回では足りない

**invoice が PR #767 で実証**（hub 経由で受領）:

| 回 | 通る経路 | `--limit 1000` は効くか |
| ---: | --- | --- |
| **1回目** | **Issue の新規作成**（既存が無いので `gh issue list` の結果は空） | ❌ **効かない** |
| **2回目** | **重複検出 → 既存 Issue にコメント** | ✅ **ここで効く** |

⇒ **1回で終える陽性対照は「Issue が立つ」ことしか確かめていない。**
**`--limit 1000` に直した意味は、2回目まで回さないと1バイトも検証されていない。**

🔑 **「対照が発火することを見た」の一段先。** 対照は発火している（Issue が立つ）。
**ただし発火したのは、直した経路ではない。**
⇒ **「対照が発火した」ではなく「対照が、直した経路を通って発火した」まで問う。**

**手順**:

1. `workflow_dispatch` を `simulate_failure=true` で叩く ⇒ **Issue が1本立つ**
2. 🔴 **もう一度叩く** ⇒ **新規作成されず、既存 Issue にコメントが付く**
3. テスト由来の Issue を**説明付きで閉じ**、**open 数が実験前と同数に戻る**ことを確認

⚠️ **陽性対照を回すと本物の Issue が1件立つ**（invoice 実測）。
⇒ 🔴 **適用先の艦に「テスト由来の Issue が1件立つ」と先に伝えること。**
🔑 **黙って立つと、それこそ「毎週重複を立てる装置」と見分けがつかない。**

### ✅ 適用1号 = `nene-vault`（2026-08-28 実施済み・`nene-vault#492` / `#493`）

**2段の陽性対照は実際に取れた**〔fleet 実測 20:17〜20:19〕:

| 回 | 実測 |
| ---: | --- |
| **1回目** | Issue **#494** が立った（open **17 → 18**）。**notify ジョブは skip ではなく実走**（conclusion=success） |
| **2回目** | open は **18 のまま**・**同題は1本のまま**・**#494 のコメントが 0 → 1** |
| 後始末 | #494 を説明付きで閉じ、**open が 17（実験前の基準値）へ戻った** |

🔴 **2回目のコメントの本文が2回目の run URL を指している**＝**重複検出の経路を実際に通った証拠**。

### 🔴 この実験で取れなかった層（明記する）

**「`--limit 1000` でなければ壊れる」は取れていない。** vault は open 17 で `--limit` の既定 30 の内側なので、
**`--limit 100` のままでも2段とも緑になる。**
⇒ 取れたのは **「直した経路が実行された」**までで、**「直した値でなければ落ちる」ではない。**
🔑 **取れなかった層を明記しない実験は、後から「全部確かめた」と読まれる。**

⚠️ **`--limit` を小さくする変異では再現しない**（vault の指摘）——
`gh issue list` は**新しい順**を返し、**audit Issue は立てた瞬間が最新**なので窓から落ちない。
**切り詰めが対象を隠すのは、対象より新しいものが窓を埋めているときだけ。**
⇒ 実証するには**囮を1本挟む**（#A audit → #B 囮 → #C 重複が立てば実証）。**Issue 3本のコスト。**

### 既知の落とし穴

- 🔴 **`setup-php` は `COMPOSER_NO_AUDIT=1` を立てる**（#281・3艦で再現）。
  殺されるのは **install/update に付随する暗黙の audit** で、**明示的な `composer audit` は生きている。**
  ⇒ 「setup-php を使っているから audit は死んでいる」と読まない。**暗黙は死んでいるが明示は生きている。**
- 🔴 **写す先に `schedule` が無いのに `schedule` を条件へ写すと、simulate 以外で永久に発火しない**
  （vault の backend-ci がこの形・#379）。**条件は「持っている event」から導出する。**
- 🔴 **dedup をサーバ側検索（`--search`）に置き換えない。** `--limit` 問題ごと消えるように見えるが、
  **題名が日本語だと成立しない**〔fleet 実測 2026-08-28〕:

  ```
  --search 'in:title weekly-audit' → 0 件   ← 実在するのに引けない（陽性対照が落ちた）
  --search 'weekly-audit'          → 1 件
  --search '凍結'                   → 17 件  ← 日本語は過剰一致
  --search '契約の値'                → 16 件
  --search 'キット既定'              → 7 件
  ```

  ⇒ **「引けない」か「引きすぎる」のどちらかになる。完全一致の意味論がサーバ側に無い。**
  **`--limit 1000` ＋ クライアント側 `jq` 完全一致が正しい設計。**
  🔑 **「改善」として壊しに来るのは、装置が正しく動いている時期。** だからここに書いてある。
- **PR 時の `composer audit` と週次は両方残す**（hub 裁定）。**目的が違う**——PR 即時検知と週次再検査。
  週次が要るのは **advisory が我々のコミットではなく向こう側の時計で公開される**から。
