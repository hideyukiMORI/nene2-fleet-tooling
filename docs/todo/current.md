## 測るときの作法

**実際にひっくり返ったものだけを置く。** 新しく踏んだら足す。

1. **N 回 green は陰性対照とセットで。** → **#206**
2. **「まだ落ちていない」を根拠にしない。**
3. **射程は「どこにあるか」でなく「何であるか」で数える。**
4. **不在の主張には陽性対照を1本。** 「0件」は検出器が死んでいても出る。
5. **条文化のときは、issue で発見し、正本で確定する。**
6. **本文を持つ CLI 呼び出しは本文をファイル経由で。**（#215）
7. **道具の単位を、測りたいものの単位に合わせる。** → #226 / #243
8. **空き番の判定は台帳では足りない。**
9. **自分が配る数字にも「いつの実測か」がある。** → #237 / #245
10. **「失われた作業の有無」と「リポジトリの健全性」は別の検査。**
11. **他艦・hub の報告は追試してから自分の設計の前提にする。**
12. **測る側が自分を測っているか確かめる。** → #255
13. **注意力は再現しない／経路は再現する。** → #258
14. **構造から従うことを「観測した」と書かない。**
15. **イベント直後の1確認は競合窓に当たる。**
16. **「実在する」は、どこで見たかで意味が変わる。** 内容を主張するなら `origin/main` を見る（判例43③）。
17. **不在の主張は、道具が黙って空を返す形にしない。**
18. **「装置が動いているか」は、run の有無でも測れない。** origin は **run も job も出るが step が0本・3〜6秒**。
    実欠陥の赤とは **step 数と所要秒数**で区別できる。🔴 実装は **hub の手番**／**private は監視対象外**（08-15 施主方針）。
19. **実行者名義は「道具の資格情報」であって「行為者」ではない。** `mergedBy` は常に `hideyukiMORI`。
20. **安全弁は「足さなかった」で終わらせない。外す条件まで測る。**
21. **ゲートの厳しさはエコシステムごとに違う。** `composer audit` は全 severity・`audit-ci` は high 以上。
22. 🆕 **設定ファイルの「有効な設定」は、コメントを除去して構造として読む。**
    この艦隊は撤去理由をコメントで残す作法を持つので、**作法そのものが `grep` の精度を下げる**。
    ⚠️ **外れ方が安全側に見える**（射程が過大）ので気づきにくい。
23. 🆕 **道具の目的関数を疑う。** `npm audit fix` は「advisory を消す」だけが目的で、**依存グラフの保存は目的に入っていない**。
    ⇒ **事故った本人を疑う前に、本人が使った道具を疑う。** → 判例44 ⑧
24. 🆕 **3艦で成功した型が、4艦目で事故を起こす。成功回数は安全性の証拠にならない。**
25. 🆕 **「同じファイルを配る」と「同じ検査を受ける」は別。** 受け手の CI の射程は艦ごとに違う。 → #272
26. 🆕 **「main が赤い」は run の結論だけでは読めない。** 故障注入（`simulate_failure=true`）の赤がある。
27. 🆕 **安全弁は GO が出ても外さない。** GO は「足してよい」であって「前提を確かめなくてよい」ではない。
28. 🆕 **数字を受け取ったら「どの木で測ったか」を確認する。** 08-15 は hub の数字が3回それを欠いた
    （grep 由来の射程／lockfile を grep で未検出／`main` ではなく PR ブランチの木で測った 0件）。
    判例44⑥（測った環境を一行添える）は、**出す側が守れていないことがある**という前提で受け取る。
29. 🆕 **照会は、聞かれた側の持ち物を点検させる。** 08-15 は推測が**逆**だった照会1行から、
    hub の常設計器 `ci-watch` の欠陥が3件出た（文字列マッチのみ／`run:` とコメントを区別しない／`git fetch` しない）。
    **当たり外れと無関係に相手の側で点検が走る**ので、迷ったら出す。

🔴 **lockfile を触るときの手順**（判例44・正本 = `_work/reports/2026-07-21-full-close-playbook.md` §7）:
0. **着手前に、その艦の CI が lockfile 以外に何を同時に要求するかを測る**（format の射程・生成物の追跡）＝ **⑦**
1. 変更前後で **`packages` の件数**を比較（縮小＝破壊の疑い。ただし**上流が配布をやめた optional binding** の消失は別）
2. 変更前後で **版が動いた全パッケージを列挙**し、**昇格/降格の向き**を見る
3. **workspaces / 複数 lockfile の有無**を先に確認する（`packages[""].workspaces`・`git ls-files`）
4. PR 本文は 0〜3 の**全数**を書く。「起点の advisory 名」だけを書かない
5. **`npm audit fix` ではなく `npm update <対象>` を狙い撃ちする**＝ **⑧**
