### 🔴 M-3 — 断の後は「リポジトリが使えるか」を別に測る

**08-05 夜に fleet で実害が出た**（records と **2艦独立**・同時刻・同型）。

壊れ方に再現形がある: **直近でマージされた PR のマージコミット（loose object）＋ その PR が触ったファイル**が
**0 バイトに切り詰められる**。fleet では `a6677d1`（#244 のマージコミット）と standards-patch の2ファイル
（302行 / 265行）が飛び、**`git status` すら fatal で止まった**。

- **「失われた作業の有無」と「リポジトリの健全性」は別の検査。** 前者が無事でも後者は壊れうる。
- 破損は**最初に触った git コマンド**で露見する（`fetch` とは限らない・fleet は `status` で踏んだ）。
  **fatal が出たら種別に関わらず走査へ進む。**
- 走査: `find .git/objects -type f -size 0` ／ **追跡ファイルの0バイト走査**
  （`git ls-files -z | xargs -0 …`）。🔴 **中身が消えてもファイルは残るので `git status` は何も言わない。**
- 修復: 空 object を削除（**先に GitHub API で当該 commit の実在を確認**）→ `git fetch` で再取得 →
  `git fsck --no-dangling` 無出力 → 切り詰めファイルは `git restore` → 0バイト走査で他に無いことを確認。
- 🔴 **fleet の2ファイルは、たまたまマージ済みだったから復元できた。未コミットなら静かに消えていた。**

## 測るときの作法

**実際にひっくり返ったものだけを置く。** 新しく踏んだら足す。

1. **N 回 green は陰性対照とセットで。** 主張は「直った」ではなく**余裕の量**で書く。→ **#206**
2. **「まだ落ちていない」を根拠にしない。** 緑の記録は**余裕がどれだけ残っているかを何も語らない**。
3. **射程は「どこにあるか」でなく「何であるか」で数える。** パス判定のまま配ると
   **永久に緑で何も検査しないゲート**を配ることになる（＝ G-6 に自分で違反）。
4. **不在の主張には陽性対照を1本。** 「0件」は検出器が死んでいても出る。
5. **条文化のときは、issue で発見し、正本で確定する。** issue は正本のスナップショットであって正本ではない。
6. **本文を持つ CLI 呼び出しは本文をファイル経由で。** `gh … --body "…"` は
   **壊れても呼び出しは成功する**（#215）。
7. **道具の単位を、測りたいものの単位に合わせる。** 素の `grep 'GHSA-…'` は jsonc の**コメントまで拾い**、
   艦隊の mh99 を **14艦**と誤測した（正 5艦）。🔴 **撤去済みの艦ほど誤検出される**向きだった。→ #226 / #243
8. **空き番の判定は台帳では足りない。** 未確定の予約は台帳に載らない（上記 EX-8）。
9. **自分が配る数字にも「いつの実測か」がある。** 18時間で 23件/8艦 → 20件/5艦。→ #237 / #245
10. 🆕 **「失われた作業の有無」と「リポジトリの健全性」は別の検査。**
    作業が無事でもリポジトリは壊れうる。**中身が消えてもファイルは残るので `git status` は何も言わない**
    （上記 M-3・2艦独立で確認）。
11. 🆕 **他艦・hub の報告は追試してから自分の設計の前提にする。** 疑うためではなく、
    **その数字の上に自分が積むから**読む。08-05 は origin の申告5点を全部引き直して全部当たり、
    hub の「失われた作業なし」は結果として正しかったが**リポジトリは使えない状態**だった。
