## 測るときの作法

**実際にひっくり返ったものだけを置く。** 新しく踏んだら足す。

> 🔑 **前文 — 一経路の結論を信じるな。**
> 以下の作法は、ほぼ全部がこの一般則の各論である（転写を疑う／道具の除外を疑う／数え方を疑う／
> 木を疑う／射程だけで決めるな）。
>
> **一致の価値は「確信が増す」ことではなく、「もう動かない」と言えるようになること。**
> 一経路の結論は、**正しくても「たまたま当たった」と区別がつかない**。区別がつかないものは、
> 次の人がまた測り直すか、**測り直さずに転写する**。🔴 **転写されるのは「一致していない結論」のほう。**
> （08-19 の `field` の偽の実害は、実測を経ずに**4段転写**された。）
>
> 🔴 **他人の計器を疑う前に、自分の木を疑う。** **渡された数字より、自分で出した数字のほうが危ない**——検算しないから。
> しかも「他人の計器に欠陥がある」方向の主張は、**当たれば大きいぶん、外すと判定軸ごと信用を焼く**。
>
> フリート全体の正本 = `_work/advice.md`（「一経路の結論を信じるな」・08-19 の一致4件の表つき）。

1. **N 回 green は陰性対照とセットで。** → **#206**
2. **「まだ落ちていない」を根拠にしない。**
3. **射程は「どこにあるか」でなく「何であるか」で数える。** → 08-19 に自分の玉の母集団で出た（`type: library` の艦が混ざっていた）
4. **不在の主張には陽性対照を1本。** 「0件」は検出器が死んでいても出る。
5. **条文化のときは、issue で発見し、正本で確定する。**
6. **本文を持つ CLI 呼び出しは本文をファイル経由で。**（#215）
7. **道具の単位を、測りたいものの単位に合わせる。** → #226 / #243
8. **空き番の判定は台帳では足りない。**
9. **自分が配る数字にも「いつの実測か」がある。** → #237 / #245
10. **「失われた作業の有無」と「リポジトリの健全性」は別の検査。**
11. **他艦・hub の報告は追試してから自分の設計の前提にする。**
12. **測る側が自分を測っているか確かめる。** → #255
13. **注意力は再現しない／経路は再現する。** → #258
14. **構造から従うことを「観測した」と書かない。**
15. **イベント直後の1確認は競合窓に当たる。**
16. **「実在する」は、どこで見たかで意味が変わる。**（判例43③）
    🆕 08-19 の実例: `NENE2/frontend` を**ローカルで**監査すると high 4 / moderate 1 が出るが、**`origin/main` の lock では 0件**。
    ローカルが**2コミット古かった**だけだった。⇒ **同じコマンド・同じ検出器で、木が違うと答えが変わる。**
    **「Dependabot が見落としている」と言う前に、自分の木を疑う。**
17. **不在の主張は、道具が黙って空を返す形にしない。**
18. **「装置が動いているか」は、run の有無でも測れない。**（origin は run も job も出るが step が0本）
19. **実行者名義は「道具の資格情報」であって「行為者」ではない。**
20. **安全弁は「足さなかった」で終わらせない。外す条件まで測る。**
21. **ゲートの厳しさはエコシステムごとに違う。** → `_work/reports/2026-08-19-audit-gate-severity-asymmetry.md`
22. **設定ファイルの「有効な設定」は、コメントを除去して構造として読む。**
23. **道具の目的関数を疑う。** → 判例44 ⑧
24. **3艦で成功した型が、4艦目で事故を起こす。成功回数は安全性の証拠にならない。**
25. **「同じファイルを配る」と「同じ検査を受ける」は別。** → #272
26. **「main が赤い」は run の結論だけでは読めない。**（故障注入の赤がある）
27. **安全弁は GO が出ても外さない。**
28. **数字を受け取ったら「どの木で測ったか」を確認する。**
29. **照会は、聞かれた側の持ち物を点検させる。**
30. 🆕 **具体的な数字ほど疑う — 数字は転写に強く、検証に弱い。**
    08-19 に渡された「field の実害（lock v1.8.2・check 5 errors）」は、**4段転写されるあいだ誰も測っていなかった**。
    `正本=...` は「そこに**書いてある**」であって「そこで**測った**」ではない。
    🔑 **構造から不可能を示せることがある** — `^1.11` は v1.8.2 を解決できないので、**現物を見る前に矛盾が出せた**。
31. 🆕 **不在・規模の主張は、道具の除外が効いているか確かめてから出す。**
    `find` で `.php` を123本と数えたが、**115本はキャッシュの中身**で、実数は8本だった。
32. 🆕 **測っていないものを「0」と書かない。** Dependabot の 403 は「無効」であって「脆弱性なし」ではない（**22リポ**）。
33. 🆕 **出所の違う数字を同じ表に並べない。** 「sakura-FT 3件」は Dependabot ではなく `composer audit` 由来の疑い。
34. 🆕 **数え方を先に決めてから数える。** 同じ母集団が **98（延べ）/ 66（直す箇所）/ 35（判断）** になる。
    **マニフェストが複数ある艦は延べが倍化する**（records-site = 22×2）。
35. 🆕 **手元と CI は別の検出器であり、どちらが厳しいかはルールごとに違う。** → #282
    「新しい版なら安全」も「CI の固定版のほうが甘い」も、**両方とも外れる**。
36. 🆕 **検査は痕跡を残す形で置く。** ログに `run:` 行が残らない検査は、**存在しない検査と区別できない**。 → #281
37. 🆕 **待つと決めた玉は、待つ先の期日に置く。** 行の末尾に「今日はやらない」と書いても、**期限だけが取り残されると
    毎日 🔴 で出る**（hub が 08-19 に `NENE2` の行で実際に踏んだ）。⇒ **板が「本当に遅れているもの」と
    「待つと決めたもの」を区別できなくなる。** 待ち先が別の玉なら、**その玉と同じ期日に揃える**（＝同じ束だと示す）。
    🔴 **適用条件**: **期日を置けない待ちが存在する。** 待ち先が**他人の release**（例: `vitepress` が vite 6+ を引く版を出すこと）なら、
    こちらから期日を決められない。⇒ **それは「待ち」に分類してはいけない。放置になる。**
    **期限つき例外（ID／理由／期限／解除条件）で受けるか、玉ごと別の解に振り替える。**
38. 🆕 **射程と可達性は別の軸。**「1回の判断で N リポ片づく」は、**その判断が実行可能であることを含意しない**。
    08-19 に自分でこれを踏んだ: `vite` / `esbuild` を「9リポ・5リポに効くから先に」と推したが、
    **4リポとも `fixAvailable=False`**（`vitepress` 1.x が `vite ^5` に固定・vitepress に 2.x は無い）＝**閉じられない玉**だった。
    ⇒ **射程だけで順序を決めると、いちばん広い玉がいちばん動かない玉だったということが起きる。**
    🔑 **「修正版がある」と「このリポで上げられる」は別の主張。** advisory 台帳（`first_patched_version`）の値を、
    **リポの可達性の主張に使わない。**
