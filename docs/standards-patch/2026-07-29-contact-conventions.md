## 1. ① 時計だけを偽装する／壁時計を直接読まない

起草側の明示要求:

> ①は**フロントとバックで別の章に分かれて書かれがち**だが、実体は同じ規律（時刻を外から与える）である。
> **「テスト」章と「実装」章の両方に置き、相互参照**してほしい。片方だけ読む人が必ずいる。

これは #154 の ⑥（規約の届け先）の「読者ごとに1箇所ずつ置く」と**同じ主張**である。両 patch を収載するときは
**⑥ を先に立て、本条をその適用例として参照させる**のが筋（W0b の収載順への申し送り）。

### 条文 A — テスト側（暫定 `02 §5`・本来はテスト章）

> **時計の偽装は `Date` だけに限る**（MUST）。
>
> 現在時刻に依存する振る舞いをテストするときは、**タイマ全部ではなく `Date` だけ**を偽装する
> （vitest なら `vi.useFakeTimers({ toFake: ['Date'] })` → `vi.setSystemTime(...)`）。
>
> 素の `useFakeTimers()` は `setTimeout` / `queueMicrotask` まで止めるため、**MSW・react-query・
> Testing Library の待機が動かなくなる**。このときテストは「時刻がズレて落ちる」のではなく
> **タイムアウトで落ちる**——**原因が時計だと気づけない形で壊れる**。
>
> ＝ 症状がアサーション不一致ではなく待機タイムアウトになるため、調査が「非同期がおかしい」方向へ逸れる。
> **時計を止めた副作用だと気づくまでが遠い**のが、この規約を MUST にする理由である。
>
> → 実装側の対応条文は **条文 B**（相互参照）。

### 条文 B — 実装側（`05 §7` に D4 として既存・条文本体を `02` へ）

> **壁時計を直接読まない**（MUST NOT）。
>
> 実装は `date()` / `time()` / 引数なし `new DateTime()` 等で現在時刻を直読みしてはならない。
> `ClockInterface`（本番 `UtcClock`）を注入し、テストは固定時刻の実装を差し込む。
>
> これは規約文だけでなく**機械ゲートで強制する** ＝ NENE2 conformance ルール **D4**。
>
> → テスト側の対応条文は **条文 A**（相互参照）。

### 根拠（実測・落とすと痛い具体）

- ダッシュボードの「受信の推移（7日）」は**今日を基準に7日窓**を切るので、素で書くと日付が変わるたびに落ちる。
  `frontend/src/pages/home/HomePage.test.tsx:116` で `vi.useFakeTimers({ toFake: ['Date'] })` ＋
  `vi.setSystemTime(new Date(2026, 6, 22, 10, 0, 0))` として固定した。同ファイルのコメントがそのまま条文の核心:

  > Fake only Date so the 7-day window is deterministic; MSW/react-query keep real timers.

- 🔴 実装側は同型を**機械ゲートで**止めている。2026-07-29 に監査ログ CSV 書き出し（contact #522）のハンドラを書いた際、
  ファイル名生成に `date('Y-m-d')` を使ったところ **conformance D4 が即エラー**にした:

  ```
  [ERROR][D4] src/Audit/ExportAuditEventsHandler.php:31 Raw current-time read date() with no explicit
  timestamp. Inject Nene2\Http\ClockInterface (Nene2\Http\UtcClock in production) instead.
  ```

  `ClockInterface` 注入に直して緑。**レビュー待ちにならずその場で直る**のがこの型の価値。

### 機械強制の状況

🟢 **実装側（条文 B）は既に稼働している**（NENE2 conformance D4）。フロント側（条文 A）に等価な検査は無い。
`vi.useFakeTimers()` を `toFake` なしで呼んでいる箇所の検出は **eslint ルールとして実装可能**（`no-restricted-syntax` 相当）。
→ 別 issue（§6）。

## 2. ② 非同期リスト遷移は「現れた」で待つ

### 条文（暫定 `02 §5`・本来はテスト章）

> **非同期リスト遷移の待ち方**（MUST）
>
> 一覧のページ遷移・絞り込み・並べ替えのように**前の内容が残ったまま次が来る** UI
> （react-query の `placeholderData: keepPreviousData` 等）のテストでは、**「前の行が消えたこと」を待たない**（MUST NOT）。
> 消えるタイミングは次のフェッチと競合するため、遅い CI で**負のアサーションがレースに負けてタイムアウト**する。
>
> **「次の行が現れたこと」という正のシグナル**を `findBy*` で待ち、**その後に**「前の行が無いこと」を
> 同期アサーションで確認する。
>
> あわせて、**そのコンポーネントが実際に撃つリクエストは全部スタブする**（MUST）。1本でも未マッチのハンドラが残ると、
> MSW の未処理リクエスト経路が**遷移中のタイミングを揺らす**。

### 派生条文 ②'（収載先が別 — `05 §6` の「機能追加時のチェックリスト」）

起草側の明示要求:

> ②の後半（**新しいクエリを足したら既存テストのスタブも足りなくなる**）は、テスト章よりも
> **「機能追加時のチェックリスト」に置くほうが効く**。実際 `/admin/tags` は**タグ機能を足したときに増えた**もので、
> 壊れたのは**無関係な一覧テスト**だった。

> **機能追加時**: 新しいクエリ（API 呼び出し）を追加したら、**その機能のテストだけでなく、
> 同じコンポーネント木を描画する既存テストのスタブも足りているか**を確認する。
> 新クエリは**追加した機能と無関係なテストを壊す**。

### 派生条文 ②'' — フレークの扱い

> **フレークを直したら、直後の1回ではなく、その後の実 CI 実行で再発を監視する**（MUST）。
> 「ローカル N 回 green」は**必要条件であって十分条件ではない**（CI の遅さは再現できない）。
> 「de-flake 済み」と書いて終わりにしない。
>
> 🔴 **フレークが2回直らなかったら、テストではなく実装を疑う**（MUST）。
> 「待ち方を変える」修正が続くときは、**状態が巻き戻されている**可能性を先に潰す
> （マウント時に走る `useEffect` のタイマ・初期値と同値での再コミット等）。
> **待ち時間の延長で直らないフレークは、「待てば来るものが来ていない」＝競合ではなく取り消しである。**

### 根拠（実測・落とすと痛い具体）

対象は受信箱一覧の「次ページへ進むと範囲表示が更新される」テスト（`frontend/src/features/list-submissions/ui/SubmissionList.test.tsx`）。
**3回の修正を要した**経緯そのものが根拠になっている:

| 回 | 日付 | 対処 | 結果 |
|---|---|---|---|
| 1 | 07-23（#478 → PR #479） | 「前ページの行が消えるのを `waitFor` で待つ」に変更 | ❌ **直らなかった**（負の条件を待つ形が残っていた） |
| 2 | 07-24（#508 → PR #511・`eebf494`） | ① `keepPreviousData` で負のアサーションがフェッチとレース ② `/admin/tags` 未モック、の2点を切り分け → `findByText('Sender 21')` で待ち、`/admin/tags` をスタブ。ローカル8回 green | ❌ **CI で再発**（contact PR #523 の Frontend CI 初回 run 30383899428・17:40 UTC で落ち、再実行で通った＝3回目の再発） |
| 3 | 07-29（#528 → PR #529） | 🔴 **原因はテストではなくコンポーネントだった**。検索デバウンスが**マウント時にも 300ms タイマを仕掛け**、それが `setPage(0)` を撃つため、**画面を開いて最初の 300ms の操作が黙って取り消されていた**（「次へ」がページ1に戻される）。値が実際に変わったときだけタイマを仕掛ける形に修正 | ✅ **解決** |

- 🔴 **3回目で分かったのは「テストの待ち方の問題ではなかった」こと**。1・2回目はいずれも待ち方をいじる修正で、
  **正しい方向ではあったが原因ではなかった**。②'' が MUST なのはこの経緯による。
- 🔴 **利用者への実害**: これは**テストだけの問題ではなかった**。実装のバグなので、

## 4. ④ CSV は「セルの先頭文字」で式インジェクションを殺す

### 条文（`02-data-flow.md` に「出力・書き出し」節を新設 = 新 §9.5 として収載）

> **§9.5 CSV 書き出し**
>
> CSV 書き出しでは、**どのセルも `=` `+` `-` `@` で始まらない**ことを構造的に保証する（MUST）。
> 表計算ソフトはこれらで始まるセルを**数式として実行**するため（CSV injection / formula injection）、
> ユーザ入力がそのまま先頭に来る設計は、エスケープの有無に関わらず危険である。
>
> 望ましいのは**エスケープではなく構造**——値を **JSON でくるむ**（必ず `{` `[` `"` 始まり）、
> 数値・日時・語彙（enum・識別子）だけを裸で出す、という**列設計**にする。
>
> 🔴 **上流化（共通 `CsvWriter` 化）するときは、この性質を「たまたま」から「保証」に格上げすること**（MUST）。
> 共通ライブラリは任意の文字列を受け取れてしまうので、**writer 側で先頭文字を検査**し、
> 危険な先頭文字なら**接頭辞を付ける等で無害化**する責務を持たせる。

### 根拠（実測・落とすと痛い具体）

- contact の監査ログ CSV 書き出し（#522 / PR #523）は、hub レビューで
  「**JSON 包みでセルが `{`／数字／語彙始まりになるため式インジェクションが構造的に不可**」という性質を確認した。
- 実際の列構成: `id`（数字）・`created_at`（数字始まりの日時）・`actor_user_id`（数字 or 空）・
  `action`（`contact_form.updated` 等の語彙）・`entity_type`（語彙）・`entity_id`（数字 or 空）・
  `before` / `after`（**`json_encode` した結果＝必ず `{` 始まり**）。**利用者の自由入力がセル先頭に来る経路が無い。**
- 🔴 **これは設計の結果であって、明示的な防御ではない**。「送信内容そのもの」を列として足した瞬間に成立しなくなる。
  受信箱 CSV `submission.exported` は `field_values` を JSON で出しているので現状は同じく安全だが、
  **将来フィールドを列展開したら破れる**。
  ＝ **上流化の際に writer 側の検査として固定しないと、静かに失われる性質**である。

  > これは #154 の ⑤（「意味の違う正常値」）と同じ型である——**安全なのが偶然で、壊れても誰も気づかない**。
  > 両 patch を収載するとき、本条を ⑤ の適用例として相互参照させるとよい（W0b への申し送り）。

### 機械強制の可能性（別 issue）

🟢 可。共通 `CsvWriter` を配布物として持つなら、**writer 側の先頭文字検査は writer 自身のテストで担保できる**
（＝ 検査器を別途書く必要がない、最も安いパターン）。加えて「CSV を組み立てているのに共通 writer を経由していない箇所」の
検出は conformance ルールとして書ける。
