## 1. 族の設立 — 「導入 ≠ 実行」ガード族

### 1.1 族の定義（条文）

> **「導入したこと」を検査するゲートは、「効いていること」を検査していない**（原則）。
> 導入を検査するゲートを置いたら、**実行時に効いていることを検査する別のゲート**を対で置く（MUST）。
> 前者の green は後者の証拠にならない。

G-6（検査器は fail-closed・検査不能は unknown）が**検査器の側**から言っていることを、**被検査対象の側**から言い直したもの。G-6 は「検査が走らなかったのに green を出すな」、本族は「**検査は走ったが、それは導入の検査であって実行の検査ではない**」。

### 1.2 なぜ族として立てるか（起草側の主張＋fleet の追認）

serve の主張をそのまま採る:

> 規約としては「導入の検査」と「実行の検査」を別立てで要求するのが正だと考える。

fleet の追認理由: **族として立てないと、同じ主張が章をまたいで別名で散る**。実測すると、同じ型の実例が**すでに8件**存在し、収載先は4つの章にまたがる（§5 の台帳）。1件ずつ各章に収載すると、**8件目を踏んだ人が「これは既知の型だ」と気づく手段が無くなる**。実際 §5 メンバー7 は、集約先の番号が無いまま伝聞され**還流先の指定が2度取り違えられた**。

## 2. ① TC-x（→ EX-1）トークン参照の解決性

### 条文（`03-styling-theming.md` に収載）

> 契約テーマファイルに宣言された CSS カスタムプロパティと、プロダクトソース内の
> **fallback を持たない** `var(--x)` 参照を突合し、未宣言トークンを指す参照が
> 1件でもあれば CI を落とす検査を各リポに置く（MUST）。
>
> - 検査対象: テーマ CSS ＋ `src/` 配下の `.css` / `.ts` / `.tsx`（テストは除外）
> - **fallback 付き参照は対象外**（`var(--pct, 0%)` のように実行時にインライン style や埋め込み親が値を供給する設計。**fallback がその契約**であって欠落ではない）
> - 失敗時は `file → var(--token)` の形で**どこの何が**外れたかを出す
> - 「宣言済みトークンが 0 件」でテストが空振り成功しないよう、**パーサ自体のガード**を持つ（G-6 の自己適用）

### 根拠（serve 実測・fleet では再実測していない）

CSS の `var(--x)` は `--x` が未宣言でも**エラーにならない**。宣言ごと破棄され、要素は継承値で描画される。**型検査・lint・テスト・Storybook ビルド、どれも通る。**

| 参照 | 実際に起きていたこと | 開いていた期間 |
|---|---|---|
| `var(--danger)` ×2（Input/Select） | エラー時の枠が**赤くならない** | W1 以前から |
| `var(--fg)` ×2（ブランドマーク） | 下段カード2枚が**塗られない** | 同上 |
| `.danger` クラス（未定義・9箇所） | **コンソールの全エラーメッセージが本文色**で描画 | 同上 |

`--danger` / `--fg` は serve のトークン語彙に**一度も存在したことがない**。issue（serve #156）として起票はされたが **15日 open のまま**だった。**装置（人の目）は動いていたが、機械検査が無かったので優先度が上がらなかった。**

### 実装の型（写せる形）

`nene-serve/frontend/src/shared/ui/theme/serve-css-contract.test.ts`（serve PR #197）

```
describe('serve.css token contract', () => {
  it('declares tokens at all (guards the parser itself)', …)   // 空振り防止
  it('has no fallback-less var() reference to an undeclared token', …)
})
```

serve 実測: 宣言 58 / 使用 58 / 宙吊り **0**（**PR #197 時点**）。負テスト実証: `var(--fg)` を戻すと `shared/ui/icons.tsx → var(--fg)` を挙げて fail。

### 🔴 移植時の注意 — 宣言側集合の取り方（起草側の回答・2026-08-04 追記）

> **出典**: #161 の起草側同意確認（指示書 `_work/handoff-serve-161-conventions-review-2026-07-31.md` の Q2）に対する serve リナの回答。**serve の実測であり fleet では再実測していない。**
> 実装の受け皿は **#222**（TC-x 検査器の配布物化）。

**一番危ないのは「艦が単一テーマである」ことを前提に固定すること。単一は永続とは限らない。**

serve 実測（**08-04 時点・serve main=`73d072e`**）: 宣言側は `shared/ui/theme/serve.css` **1本のみ**（カスタムプロパティ宣言 **135**・`frontend/src` 配下の他 `.css` は **0本**）。**ただし serve #175（W6/stage2）で「トークンを専用テーマファイルへ分割する」ことが確定済み** — つまり serve は「宣言ファイル1本 → 複数」へ移る瞬間が**日程に載っている**艦である。
※ 上の「宣言 58」は PR #197 時点の数字で、この **135 とは時点が違う**（どちらも時点つきで読むこと・上書きではない）。

1. **glob の和集合で取る（1ファイル固定にしない）。** 検査器が「テーマファイル＝1本」を引数や既定値で固定すると、分割した瞬間に**分割先の宣言が集合から落ち、宙吊り参照が宙吊りに見えなくなる＝静かに偽陰性へ落ちる。しかも gate は緑のまま。**
   起草側の言: これは **EX 族そのものの再発型**（導入されているが実行されていない）であり、**族の検査器が族の失敗モードを踏む**のは避けたい。
   （`themes/default.css` 等を持つ艦がそのまま写すと**別テーマで宣言されたトークンを「未宣言」と誤判定する**、という当初の注意はこの1点に含まれる。）
2. **集合サイズの陽性対照を検査器自身に持たせる**（0 件、**または想定より縮んだ**なら fail）。パス変更・リネーム・分割で集合が空になったとき、参照側が「解決不能」ではなく「照合対象なし＝素通り」に倒れる実装だと**緑のまま無害化する**。
   📌 これは**新条ではなく上の条文4点目（「宣言済みトークンが 0 件で空振り成功しないようパーサ自体のガードを持つ」）の強化**である — 「0 件」から「想定より縮んだ」へ広げる。**族の台帳に別メンバーとして二重計上しないこと。**「想定」の持ち方は #222 の設計論点。
3. **fallback 付き参照の除外はファイル単位でなく参照単位で。** 条文どおり「fallback がその契約であって欠落ではない」ので、分割で `var(--x, fallback)` が別ファイルへ移っても判定が変わらないこと（＝**集合の取り方に判定が依存しないこと**）を**陰性対照で固定**する。
4. **ビルド後ではなくソースの集合を、構文（`--x:`）で取る。** serve は Tailwind 非採用の手書きデザインシステム（OKLCH）で、`@theme` を宣言源とする艦と素の CSS カスタムプロパティを宣言源とする艦が**両方フリートに実在する**。**`@theme` ブロック前提にすると非 Tailwind 艦で集合が空になる**（＝踏み所2に直結）。
   🔗 非 Tailwind 艦は fleet 実測で **4艦（concierge / serve / corpus / suite）＝ #163 と同じ母集団**。設計時に #163 と突き合わせること。

**検収**: 起草側が **serve #175 の分割前後を実験台として提供**すると申し出ている（分割前後で同じ検査器を回し、「和集合実装なら結果が変わらない／1ファイル固定なら緑のまま無害化する」を実測で出す）。段取りは #222。

## 3. ② DR-x（→ EX-2）未着地の出口 — 記録は出口ではない

### 条文（新章 `06-testing-verification.md`・暫定 `05 §5`）

> 日報に「判断待ち」「留置」「未検証」「要相談」として書いた項目は、同じセッション内で
> **issue**（単一リポで完結・判断や調査が要る）または **board**（複数リポ横断・期日がある）
> のいずれかに落とす（MUST）。**日報への記載のみで閉じてはならない。**
>
> - 落とし先を書けない項目が残った場合、**そのこと自体を日報の末尾に明示**する
> - 判定基準は「**次にこれを見る人は、どの一覧を見て気づくか**」。その一覧が「その日の日報」しかないなら、出口が無い

### 根拠（serve 実測・fleet では再実測していない）

serve の 2026-07-18 日報は、孤児ブランド WIP（ブランド刷新9ファイル）を**きちんと記録していた**。索引にも1行あり、hub 裁定で「意匠領域なので留置」まで決まっていた。

それでも **11日後に `git ls-remote` と main の ref 差分で再発見する羽目になった**。PR も issue も無いので PR/Issue ビューに出ず、日報は日が変われば読み返されない。**「留置」という決定は記録されたが、留置されたものを次に誰が見るかがどこにも書かれていなかった。**

2026-07-29 に issue（serve #194）へ落として初めて、open issue 一覧＝**セッション開始時に必ず見る場所**に現れた。

### なぜ族の一員か（起草側の対比表をそのまま採る）

| | 機械の側 | 人の側 |
|---|---|---|
| 動いていた装置 | ゲート（lint / check / CI） | 記録（日報） |
| 検査されていたこと | 「入れた」 | 「見つけた」 |

## 4. ③ DA-x（→ EX-3）時限つき例外の解除条件は「壊れているもの」で書く
