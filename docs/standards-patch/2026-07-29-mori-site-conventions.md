## 1. ① 折返しに連動させる寸法は `@container` で発火させる

### 条文（`03-styling-theming.md §6.5` として収載）

> **§6.5 折返し連動寸法**
>
> flex / grid の**折返しに連動して変わる寸法**（折返し時に画像や要素のサイズを変える等）は、
> `@media`（viewport 幅）ではなく **`@container`（行の実利用幅）で発火させる**（MUST）。
>
> viewport 幅はスクロールバー幅を含むが、折返しは行の content 幅で決まる。`@media` で書くと
> 両者が**スクロールバー幅ぶんズレて別々のタイミングで切り替わる**。
>
> 同じ構図は `100vw` にもある（`100vw` はスクロールバーを含むので横スクロールが生える）。
> **「viewport 幅」と「コンテンツの実利用幅」を同一視しない**、が本条の一般形である。
>
> **例外は認める。ただし記録を残すこと**（MUST）。`@container` を使うには親に `container-type: inline-size`
> が要り、これは**インライン軸のサイズ contain** を課すため、**幅が中身によって決まる設計**
> （`width: fit-content` ／ テーブル的レイアウト ／ 内容依存の intrinsic sizing）とは**両立しない**。
> ＝ `@container` 化できない正当なケースが実在する。
> そのときは `@media` を使ってよいが、**なぜ `@container` 化できないのかをコード上のコメントに残す**。
> **記録の無い `@media`（折返し連動の寸法）は違反とする。**
>
> ＝ 逃げ道の無い MUST は、守れない場面で**黙って迂回される**（別の場所に `@media` を書く・閾値をハードコードする等）。
> それは規約が守られているように見えて実態が違う状態＝**⑤ の「意味の違う正常値」そのもの**である。
> 記録を要求することで、**違反と正当な例外を区別できる**ようにする。

### 派生条文（①' — 収載先が別）

> **検証手段の限界**: 上の不整合は**スクロールバーを持たない headless ブラウザでは再現しない**。
> したがって「**headless で通ったから大丈夫」は根拠にならない**（MUST NOT: headless の green のみを
> レイアウト検証の根拠として提出すること）。
>
> 同型は他にもある——**フォント環境**（システムフォントの有無で折返し位置が変わる）・**IME**（変換候補ウィンドウ）・
> **hover / pointer の有無**（タッチ端末で `:hover` が張り付く）・**高 DPI**（1px 境界の丸め）。
> いずれも headless の既定値では再現しない。実ブラウザで確認するか、**構造的に消す**（後者を推奨）。

🔴 **この派生条文の置き場所は未解決**。起草側の要求は明示的である:

> 上の最後の2文（「headless で通ったは根拠にならない」）は、CSS の条文に埋めると **CSS を書く人しか読みません**。
> 実際にはこれは**検証手段の条文**なので、①の中に残したうえで、**「検証・テスト」の章にも同じ一文を置いてください**。

規約 v1 に横断的な「テスト・検証」章が存在しないため、**現時点では要求を満たせない**。§7 で上申する。
暫定的に `05 §5`（CI ゲート一覧）へ置くが、これは**読者が違う**（CI を組む人であって、テストを書く人ではない）。

### 根拠（実測・落とすと痛い具体）

- commit **2573695** `fix: sync portrait resize with wrap via @container (was @media = scrollbar-offset)`。
- 施主報告は「段落ちと画像リサイズのタイミングが**数 px** ズレる」という、コードを見ても分からない類のものだった。
- 中央化は `margin auto` でブレークポイント非依存にしてあったが、**拡大（280px 化）だけが `@media` に残っていた**。
- 修正: ヒーロー行を `container: hmhero / inline-size` 化し、拡大を `@container (max-width: 行実幅)` へ。
  閾値は折返し境界の行実幅を**実測**して決めた（JP ≤667 / EN ≤774）。
- 検証は playwright で境界を **1px 刻み**に動かし、wrap と 280 化が同一幅で flip することを確認。
- 🔴 **この不具合は headless（スクロールバー非表示）では再現しなかった**。「幅を変えて撮って比べる」型の自動検証をすり抜ける。

### 機械強制の可能性（実装は別 issue）

🟡 部分可。stylelint で「`@media` の条件式に `max-width` を持つ規則が、`container-type` を持つ祖先の子孫要素の寸法を触っている」ことの検出は**静的には困難**。現実的に判定できるのは以下:

- `100vw` の使用検出（`03 §2` の CSS 流入経路検査に追加しうる）— **loud reject ではなく warn＋waiver 運用が妥当**（`100vw` が正当な場面はある）。
- `@container` を使うファイルに `container-type` 宣言が存在するかの整合検査。

## 2. ② 生成ビルドの文字列置換は checked-replace

### 条文（`05-enforcement-migration.md §6.7` として収載）

> **§6.7 生成ビルドにおける文字列置換**
>
> 生成ビルドで外部由来のマスターを文字列置換するときは、**素の `replace()` を使わない**（MUST NOT）。
> 置換前に**出現回数を検証**し、想定と違えば例外で落とす（fail-fast）。想定回数が固定なら
> `n=期待値` で厳密一致、可変なら「1回以上」を検証する。
>
> 素の `replace()` は対象文言が1字変わっただけで**黙って no-op** し、ビルドは exit 0 で通り、
> **訂正が消えた成果物がそのまま本番に出る**。「成功か例外か」の二択だと思っている経路に、
> **黙って何もしない第三の道**がある。
>
> **存在チェックだけでは足りない**。`if old in b` だけだと、同じ文字列が2箇所に増えたとき
> 両方が置換されて**意図しない側まで書き換わる**。だから count を見る。
>
> checked-replace は**アンカーが一意であること**とセットで初めて効く（→ §3.4）。
>
> 🔴 **検証を `assert` で書いてはならない**（MUST NOT）。Python の `assert` は **`-O` を付けると文ごと削除される**ため、
> 最適化フラグ1つで**検証だけが黙って消え**、素の `replace()` と同じ挙動に戻る。
> 明示的な例外送出（`raise BuildError(...)`）にすること。

### 派生条文（`05 §0` メタ規約へ1文・⑤と接続）

> **安全網そのものが沈黙しうる経路を持ってはいけない。**

### 根拠（実測・落とすと痛い具体）

- `tools/build.py` の `rep()` / `rep1()`（hub 事後レビュー 2026-07-24 で全 `b.replace()` を移行）。
- 🔴 想定していた事故は「インボイスの**登録番号あり**という虚偽公称が本番に復活する」。当時は適格請求書発行事業者の
  **登録前**で、マスターの「登録番号あり」表記を build 側で「準備中」に訂正していた。マスター刷新で文言が1字でも変われば
  その訂正だけが静かに落ち、**法的にまずい公称が本番に出る**。ビルドは成功したように見える。
- 🔴 **この規約は、当初この規約自身の罠を踏んでいた**（hub レビュー 2026-07-28 で指摘 → 修正済み）。
  `rep()` / `rep1()` は「黙って no-op」を防ぐ仕組みなのに、**その検証を `assert` で書いていた**。
  実証（起草側が実際に走らせた出力）:

  ```
  $ python3 -O proof.py
    assert 版: 検証をすり抜けた → 静かに no-op（本番に虚偽公称が出る）
    need 版:   検証が効いた
  ```

  対処は `BuildError` ＋ `need(cond, msg)` を導入し **build.py 内の assert 8箇所すべてを置換**（rep/rep1 以外も同性質のため一律）。
- 関連: **63b727c** — アンカー文字列の選び方。汎用的な `gap` 文字列をアンカーにしていたところ、「将来同型の gap が
  他 section に出ると誤爆する」と hub レビューで指摘され、**置換対象 section の開始タグ全体（グラデ署名込み・各ページで count=1）**
  という一意な署名に変更した。

### 機械強制の可能性（実装は別 issue）

🟢 可。**本条は fleet 横断で最も機械化しやすい**:

1. ビルドスクリプト内の裸の `.replace(` / `str.replace(` 呼び出しを検出（言語別 lint ルール）。
2. **`assert` を検証に使っている箇所の検出**（Python: `-O` で消える。JS: `console.assert` は例外を投げない）。
   これは②固有ではなく**「安全網が沈黙しうる経路」の一般検査**として価値がある。
3. 参照実装として `need(cond, msg)` / `rep(b, old, new, *, n=1)` を配布物に同梱する案（要 hub 裁定）。

## 3. ③ 外部納品物に安定アンカー属性を課す

### 条文（`01-architecture.md §3.4` として収載）

> **§3.4 外部納品物の安定アンカー属性**
>
> 外部から HTML マスターを受け取ってビルドで加工する場合、**全 `<section>`（およびビルドが差し替える主要ブロック）に
> 安定した ID 属性**（例 `data-hm-id="hero"`）を**納品要件として指示書に明記**する（MUST）。
>
> ビルドのアンカーは**表示文字列（見出し・番号・コメント・クラス名）に依存させない**（MUST NOT）。
> 表示文字列は改稿・リスタイル・翻訳で変わるが、`data-hm-id` は**表示に現れない**ので変わらない。
>
> 受領物（`received/`）は**無改変で保存**して provenance を保つ。ID の導入は**次回納品から段階移行**する。
>
> **全部を等しく厳格にしない**。ビルドが実際に参照している箇所だけ ID を固定指定し、
> それ以外は綴り微修正可とする。全件を厳格にすると納品側が守れず、規約ごと形骸化する。

### 根拠（実測・落とすと痛い具体）

- `design-handoff/05-claudedesign-directive.md` **§10.5**（施主承認 2026-07-23 / hub review）、commit **47ae0ef**(c)。
- build.py は当時、section の特定に **eyebrow 番号・グラデ署名・コメント文字列**という「たまたま一意だった表示文字列」を使っていた。
  デザイン刷新のたびに**全部が同時に変わりうる**。
- ★ 実際の運用: build.py が参照している4つ（`hero` / `credit-band` / `fine-art` / `contact`）は ID 固定指定、それ以外は綴り微修正可。
- 🔴 **移行の順番が肝**。ID が入るのは**次回納品から**なので「ID アンカーへ一斉に書き換える」は**できない**（現行マスターに ID が無い）。
  そこで先に ②（checked-replace）で**黙って no-op しない**状態を作り、「移行を急がなくてよい」状況にしてから段階移行した。
  ＝ **安全網（②）を先に張る → 構造改善（③）は納品サイクルに合わせて後から**。この順序自体が条文に値する。
- 依頼の実務: 依頼は zip 1個にまとめた（カバー依頼書 `REQUEST.md` ＋ 指示書の該当章 ＋ 現行マスター4点 ＋ 推奨 ID 表）。
  **受け手が現物を持っていない前提**で、参照先ではなく現物を同梱する。

### 機械強制の可能性（実装は別 issue）

🟡 部分可。受領した HTML に対する検査は書ける（**全 `<section>` が `data-hm-id` を持つか**・**ビルドが参照する ID 集合が
受領物に存在するか**）。ただし ID 導入は次回納品からなので、**検査は当面 warn**（`kind=transition` としてレジストリ登録が妥当）。

## 4. ④ CSS-only オーバーレイの `visibility` 併用と `:target` 遅延

### 条文（`03-styling-theming.md §6.6` として収載）

> **§6.6 CSS-only（Zero-JS）オーバーレイ**
>
> `:target` によるオーバーレイ（ライトボックス等）は、`opacity` だけで隠さず
> **`visibility:hidden` ＋ `pointer-events:none` を併用**する（MUST）。`transition` は
> `opacity .18s, visibility 0s .18s`（開くときは遅延 0）。
> `opacity:0` だけでは要素が**クリックを奪い続け**、支援技術からも見えたままになる。
>
> オーバーレイに表示する**重い画像は `<img>` で置かず、`#id:target { background-image: url(...) }` に置く**（SHOULD）。
> `<img>` はオーバーレイが非表示でも**全部ダウンロードされる**が、`:target` の `background-image` は
> **開いた1枚だけ**取得される（＝ JS なしで真の遅延読み込みになる）。
> `loading="lazy"` は**オーバーレイ内の `<img>` には効かない**（viewport 内扱いになりうる）。
>
> 🔴 **適用範囲の線**: `background-image` に逃がすと画像が **DOM から消える**ので **`alt` が持てない**（MUST NOT の境界）。
> 作品画像・装飾など「見えること自体が価値で、言語化する情報を持たない」画像には可。
> **情報を担う画像（図表・スクリーンショット・グラフ）には使わない**——スクリーンリーダーから内容が失われ、
> **性能改善と引き換えにアクセシビリティが後退**する。情報画像を遅延させたいなら
> `<img loading="lazy">` ＋ オーバーレイを開くまで DOM に載せない設計を選ぶ。

### 根拠（実測・落とすと痛い具体）

- **b768b66**（CSS-only ライトボックス新設）→ **47ae0ef**(a)（遅延化）。出発点は施主の「`target="_blank"` で生画像を
  新規タブに開くのは素っ気ない」。JS を足さずに解いた。
- 実装（`site/www/index.php` の `.hm-lb`）:

  ```css
  .hm-lb        { position:fixed; inset:0; opacity:0; visibility:hidden; pointer-events:none;
                  transition:opacity .18s, visibility 0s .18s;
                  background-repeat:no-repeat; background-position:center; background-size:contain }
  .hm-lb:target { opacity:1; visibility:visible; pointer-events:auto; transition:opacity .18s, visibility 0s }
  #lb-01:target { background-image:url(/img/art/01.webp) }   /* 開いた1枚だけ取得される */
  ```

- 🔴 **実測**: 最初は全画面オーバーレイに `<img>` を10枚置いていた。**未オープンでも10枚すべてが読まれ、
  初期ロードのギャラリー DL が 1613KB**。グリッドを軽量サムネ（360×480 webp・計 244KB）に分離し、
  フル画像（900×1200）を `:target` の `background-image` へ移して **本番の初期ロードで 1613KB → 0KB**（未オープン時）。
- 検証は playwright で開閉（opacity 1 / 全画面 → opacity 0）を JP/EN 各10オーバーレイ分。

### 🔴 収載上の問題

条文後半（`alt` が持てないので情報画像には使うな）は **アクセシビリティ規約**である。規約 v1 には
**a11y の横断章が無い**（conformance キーに `e2e.axe-smoke` はあるが、対応する条文の置き場所が無い）。
①' と同じ構造の問題なので、§7 にまとめて上申する。

### 機械強制の可能性（実装は別 issue）

🟡 部分可。stylelint で「`opacity:0` を持つ規則に `visibility` / `pointer-events` が併記されているか」は判定できる
（**誤検知しやすいので warn 相当**）。`background-image` に逃がした画像が情報画像かどうかは**機械判定不能**——
ここは人間のレビュー規律として残す。

## 5. ⑤ 「意味の違う正常値」の型と停止条件

> ※ 起草側の明示指示: 「これは①〜④のような **UI／ビルドの条文ではありません**。上の『共通の型』に**重み**を与えるための
> 実証例として、末尾に置いてください」（hub 裁定 2026-07-28）。本ファイルもその指示に従い、条文ではなく
> **型の運用規則**として `05 §0`（メタ規約＝強制の原理）へ収載する。

### 条文（`05-enforcement-migration.md §0.3` として収載）

> **§0.3 意味の違う正常値**
>
> 本規約群が潰そうとしている失敗の型は、**沈黙する失敗（silent failure）ではない**。
> 実例はいずれも、エラーではなく**もっともらしい値**が入っていた（`exit 0` ／ `gap≈24h` ／ `first`）。
> したがって異常検知ではなく、**値の意味を名前で固定する**（例: `gap=` → `gap_since_ok=`）ほうが効く。
>
> **(1) 「動いたか」を、通知経路と別の場所に必ず残す。**
> 通知が届かないことと、処理が動いていないことは、**利用者からは同じに見える**。実行のたびにサーバ側へ1行追記し、
> **通知の成否に依存せず**「発火したか」を検証できるようにする。
>
> **(2) 失敗の警報を、壊れている疑いのある経路に載せない。**
> 「エラーは stderr へ（cron が拾う）」は、**その cron メールが信用できないと実証された時点で無効**。
> 生きていると分かっている経路に載せ替える。具体策: **次に成功した便が、前回の欠測を本文の先頭で自己申告する**。
>
> **(3) 「読めなかった」を「無かった」に潰さない。**
> 証跡を読む処理は、**「記録が0件」と「記録はあるが読めない」を別の状態として扱う**。同じ値に潰すと、
> 監視が死んでいること自体が**正常値に化ける**。止める必要はない（本体の処理は続けてよい）が、**黙ってはいけない**
> ＝ **「止めない。ただし黙らない」**。
>
> **(4) 状態を1つの文言に潰さない**（向きが逆の版）。「まだ来ていない」と「来るはずなのに無い」は別の状態として
> 別の文言で出す。潰すと、**正常時のノイズが、異常時のシグナルを食う**。
>
> **🔴 (5) 停止条件——どこで掘るのをやめるか。**
> 「失敗が失敗として現れない経路を潰す」は**無限に掘れる**。停止条件は「深さ」ではなく、これで置く:
>
> > **その故障が起きたとき、他の経路で必ず気づけるか。**
> > **気づけるなら塞がない。気づけないなら、階層が深くても塞ぐ。**
>
> **(6) レビューの作法**: この型は**意識して対策している人が、その対策のコードの中で、もう一度踏む**。
> 「気をつける」では防げないので、レビューで「**この対策自体はどう黙りうるか**」を1回問う。

### 根拠（実測）

事例: 日次アクセスレポートが届かなかった件（2026-07-28・hideyuki-mori-site）。同じ形の穴が **3階層、入れ子で** 出た。
**3回とも顔が同じ**——例外も出ない。ログも残る。ただし意味の違う値が静かに入る。

| 階層 | 穴 | どう黙っていたか | 発見者 |
|---|---|---|---|
| 1 | 元の不具合 | HETEML の cron は正しく発火していたが、**cron の出力メールが届かないだけ**だった。実装もデータも健全で exit 0・エラーログ 0 バイト | 施主の体感 → records リナが実測で切り分け |
| 2 | その対策の中 | run log の**最終行**を gap の基準にしたため、**`mail=fail` の行も手動実行の行も基準になり**、いちばん検知したい2つの故障が**自分で自分を隠していた** | hub レビュー |
| 3 | さらにその中 | 基準を「最後に `mail=ok` が立っている行」に直したが判定は正規表現。**行フォーマットが変われば「該当なし」＝初回扱い（`first`）に静かに落ちる**。欠測検知が死んでいる状態と初回の正常状態が**同じ値**になる | 実装者の自己点検 |

- 🔴 **階層2と3は、階層1の対策を書いている最中に生まれた**。どちらも実装直後には見えていなかった。
- 実測（**records リナの測定**——起草側の測定ではない。§9 参照）: 同系アカウントで **270日 / 14通**（本来 200通超）＝ **93% 欠落**。それでも誰も気づかなかったのは、
  **届かないこと自体が無音**だったから。
- 停止条件で判断が割れた実例（この基準があると無限に掘る話にならずに済む）:

  | | 故障 | 他に気づける経路 | 判断 |
  |---|---|---|---|
  | 階層3 | `mail=ok` の読み取り不能が `first` に化ける | **ゼロ**（値がもっともらしいので何も鳴らない） | **塞ぐ**（`unreadable` 状態を追加） |
  | 階層4 | run log が権限・破損で読めず `lines=0` ＝初回扱いに落ちる | **ある**。読めない状況では書き込みも失敗するので既存の「run log 書込不可 → stderr ＋ exit 1」で鳴る | **塞がない** |

- 参考（裏取りの作法として同型）: 「**整合した」は「判別できた」ではない**。起草側は ayane の集計境界が UTC か JST かを
  実測で「UTC 前提と整合する」と報告したが、**09:35 JST ＝ 00:35 UTC** なのでその瞬間の「前日」は
  **どちらの基準でも同じ**になる。＝ あの実測は2つの仮説をどちらも支持しており、**検証になっていなかった**。
  裏取りを書くときは「**この観測で否定できたのはどちらか**」を一度自問する。

## 6. ⑥ 規約の届け先

### 条文（`01-architecture.md §0.4` として収載・`05 §0` から相互参照）

> **§0.4 規約の届け先**
>
> **規約は「正しいこと」を書くだけでは効かない。それを破りうる人が見る場所に置いて、初めて効く。**
>
> **この型はレビューで捕まえられない。** 条文の中身の誤りはコードレビューで見つかりうるが、
> 置き場所の誤りは**コードが変わらないまま壊れる**ので、そもそもレビューの対象にならない。
> ＝ **レビューで防げないものは、置き場所で防ぐしかない。**
>
> 置き方の作法（MUST。4点とも機械判定できる形にしてある）:
>
> 1. **読者ごとに1箇所ずつ置く。** 読者が2種類いるなら2箇所に置く。片方だけでは届かない。
> 2. **同じ内容を複製しない。** 各所には**要点1行＋正本へのポインタ**だけを置く。同じ表を4箇所に書くと、
>    規約が変わったとき4箇所が食い違う。
> 3. **ポインタの宛先は寿命の長い場所にする。** `docs/todo/current.md` のような**いずれ整理・ローテーションされる**
>    場所を指すと参照が宙に浮く（リンク切れに気づけないまま残る＝これも静かに壊れる側）。正本は runbook に置く。
> 4. **ポインタ自体が、最低限の行動指示を持つ。** 参照先は**辿れないことがある**（正本が repo の外にある等）。
>    そのとき「参照先が無い」以上の情報が無いと事故は防げない。**導出や検算表は正本に、行動に必要な最小限はその場に**。
>    ※ 3 とは**別の対策**——**寿命を延ばす**のと**切れても効く**のは違う。

### 根拠（実測・落とすと痛い具体）

- **実例1**（①より）: `@container` の 🔴 は内容は CSS の話だが、**届けたい相手はテストを書く人**。
  CSS の条文に埋めると CSS を書く人しか読まない。
- **実例2**: ayane の集計は **UTC 0時境界**で、日次 export の対象日の既定値は `gmdate('Y-m-d', time()-86400)` ＝ **UTC 前日**。
  したがって **09:00 JST より前に cron を動かすと既定日が1日ぶん古い方へずれる**。

  | 実行時刻(JST) | UTC | 既定日 | JST 前日 | |
  |---|---|---|---|---|
  | 08:59 | 前日 23:59 | 07-27 | 07-28 | 🔴 ずれる |
  | 09:00 | 00:00 | 07-28 | 07-28 | ✅ 境界 |
  | 09:35（現行） | 00:35 | 07-28 | — | ✅ |

  **現行の 09:35 は境界からわずか 35 分**。「もっと早く結果が見たい」という**ごく自然な運用変更**で踏み、
  踏んでも **エラーは出ず exit 0 で、正しく見えるファイルが1日ぶん違う日付で生成される**。
  コードを一切触らずに **cron の時刻欄を1つ動かすだけで壊れる**。
- 実例2 の対処は、読者が2種類いたので2箇所に置いた: スケジュールを記述している `.sh` のコメント（＝**スケジュールを変える人**）と、
  既定値を定義しているコード行の直上（＝**コードを直す人**）。あわせて**既定値に頼らず日付を明示的に渡す**ようにした。

### 機械強制の可能性（実装は別 issue）

🟢 可。作法4点は「守れているか機械的に判定できる」形になっている——**複製の有無**（同一文の重複検出）・
**宛先のパス**（ポインタ先が短命ディレクトリを指していないか）・**読者の数**・**ポインタ近傍に行動指示があるか**。
`check:standards-doc` の同族として実装しうる。
