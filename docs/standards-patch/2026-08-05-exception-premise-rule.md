## 1. 条文（`05 §5.6`・EX-3 の直隣に収載）

> **例外（allowlist / waiver / suppression / conformance baseline）の「この艦では当てはまらない理由」は、
> 執筆時点で実測する（MUST）。**
>
> - エントリには、その理由が **機構の制約**（この艦の依存グラフ・ビルド構成の側の事情）か、
>   **上流の事実**（パッケージ・仕様・勧告の側の事情）かを**分けて書く**（MUST）。
> - **上流の事実を根拠にするときは、実測とその日付を添える**（MUST）。
>   とくに「上流に fix が存在しない」は 1コマンドで確かめられる:
>   `npm view <pkg> time` ／ `npm view <pkg> versions`。
> - **確かめずに書かれた例外は、死んだ例外になる。**
>   死んだ例外はマッチせず沈黙し、**うるさい例外より有害**である（気づく契機が無い）。

### 1.1 なぜ「機構 / 上流」を分けさせるのか

**確かめ方も、有効期限も違うから。**

| | 機構の制約 | 上流の事実 |
|---|---|---|
| 例 | 「`brace-expansion@5` の override を 1.x / 2.x 消費者へ流し込めない（named export 化で minimatch@3 が壊れる）」 | 「1.x / 2.x に patched release が存在しない」 |
| 確かめ方 | **自艦の tree を見る**（`npm ls <pkg> --all`・実走の陰性対照） | **上流を見る**（`npm view <pkg> time`） |
| 有効期限 | 自艦の依存が動くまで持つ | **外の世界が動いた瞬間に切れる**（予告なし） |
| 腐り方 | 依存更新の PR で一緒に目に入る | **誰も触っていないのに偽になる** |

両者を1文に混ぜると、**上流側が偽になっても機構側の記述に守られて読み流される**。実際に踏んだのがこの2件（§2）。

### 1.2 「死んだ例外」の定義

**書かれているが、対象のルール違反にもう対応していない例外エントリ。** ゲートは緑、エントリは残る、
そして**誰も気づかない**。うるさい例外（不要な赤を出す）は人が消しに来るが、死んだ例外は**沈黙するので消しに来られない**。

これは #237（逃げ道の総量トラッキング）の分母を静かに膨らませる。「逃げ道が23件ある」と数えたとき、
そのうち何件が**もう何も逃がしていない**のかが分からない。

## 3. 誤りの正体 — 「別の真の制約を、似て非なる制約に読み替えた」

**この診断は vault のもので、fleet の発見ではない**（§7）。fleet はこれを条文の中心に採る。

- **真の制約**: `brace-expansion@5` の override を 1.x / 2.x 消費者へ**流し込めない**
  （named export 化で minimatch@3 系が壊れる）→ **機構の制約・いまも真**
- **書かれた理由**: 「1.x / 2.x に patch が存在しない」→ **上流の事実・偽**

各系列は**自前の patch 線を持っている**（1.1.18 / 2.1.4 / 5.0.9）。系列内 bump なら export 形は変わらないので、
named export の罠も踏まない。**正解は最初から系列内 bump だった。**

読み替えが起きたのは、両者が**同じ結論（＝ここでは直せない）に着地する**からである。
結論が同じなので、理由が入れ替わっても書いた本人には違和感が無い。だから条文は
**「結論を書け」ではなく「どちらの層の理由かを分けて書け」**の形にしている。

### 3.1 なぜ族（「導入 ≠ 実行」ガード族）の一員か

例外エントリは**「書いた」時点では検査を通っている**（audit-ci は id の形式しか見ない）。
腐るのは**実行時にマッチするかどうか**である。

> **「例外を登録したこと」を検査するゲートは、「その例外がまだ何かを逃がしていること」を検査していない。**

族の定義（EX 族 §1.1）の、例外側からの言い直しになっている。
EX-3（解除条件の**書き方**）と対を成す:

| | EX-3 | **EX-9** |
|---|---|---|
| 見るところ | **出口**（いつ外せるか） | **入口**（なぜ入れてよいか） |
| 腐る場所 | 解除の判定 | **前提そのもの** |
| 実例 | 「eslint 10 波が来たら解除」＝波が来ても勧告は生きていた | 「patch が無いから」＝**書いた時点で patch はあった** |

**EX-3 だけでは今回は防げない。** vault のエントリは解除条件を「壊れているものの名前」で正しく書いていた。
**正しい出口を持つ例外が、偽の入口で作られていた。**

## 4. 配布物 — mh99 生死確認（射程は fleet が実測）

指示書で既に依頼されていた1項。本条文と同じ層（＝入口の前提の検査）なので同乗させる。

> 自艦の allowlist に `GHSA-mh99-v99m-4gvg` があるなら、**生きているかを実測する**:
>
> ```
> npm audit --json | grep mh99      # 何も出なければ死んだ例外＝撤去できる
> ```
>
> 撤去する場合、**「patch が出たから外した」と書かない**。前提が最初から誤っていたのか、
> 後から patch が出たのかは `npm view <pkg> time` とエントリの執筆日で判別できる（§2 の型）。

最初にこれを踏んだ。`grep -oE 'GHSA-...'` は **jsonc コメント中の「なぜ外したか」の記述まで拾う**。

これも本条文の実例である——**道具の単位を間違えると、生きている例外と死んだ例外の区別がつかなくなる**。
#226 で自分が書いた「道具の単位を間違えると正しい側まで壊す」の再演。

### 4.3 配布時に写経させないこと

- **「5艦に同じ誤りがある」と読ませない。** 名指ししている＝誤り、ではない。
  **各艦が自艦の tree で生死を決める。** clear の 2.1.3 も vault の版一覧も、その艦の tree の話ではない。
- **既存エントリの一斉棚卸しをここでやらない。** それは **#231** の波（既存エントリの再読）。
  本条文は**新規エントリを書く瞬間のゲート**である。両方あって初めて #237（逃げ道の総量）が意味を持つ。
