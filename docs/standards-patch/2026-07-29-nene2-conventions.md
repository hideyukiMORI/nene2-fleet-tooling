## 1. ① closing keyword をバッククォートで囲わない

### 条文（`05 §0.3` に ⑤ の適用例として収載）

> PR 本文の `Closes #NNN` / `Fixes #NNN` / `Resolves #NNN` は**バッククォートで囲わない**（MUST NOT）。
> インラインコード内では closing keyword が解釈されず、Issue が閉じ残る。
> **参照リンクは生成されるため PR 上では正常に見える** — 失敗が失敗として現れない。

### 根拠（NENE2 実測・fleet では再実測していない）

NENE2 PR #1625 の本文に closing keyword をバッククォート付きで書いた:

```
`Closes #1623`
```

PR は正常に merge されたが、**Issue #1623 は open のまま残った**。手動クローズが必要だった。

起草側（NENE2 リナ）の分析がそのまま条文化の理由になる:

- **Markdown を丁寧に書く癖があるほど踏む。** 識別子っぽいものをコードで囲むのは良い習慣なので、**むしろ丁寧な書き手が踏む**。
- **PR は緑で merge されるので失敗が可視化されない。** Issue が閉じ残ったことは、後日の棚卸しか repo-status のような点検でしか気づけない。
- Issue 駆動を敷いているフリート全艦に等しく効く。

🔴 **これは #154 の ⑤「意味の違う正常値」と完全に同じ型である**（例外も出ない・PR は緑・意味の違う結果が静かに残る／「参照リンクは生成されるので正常に見える」まで一致）。**独立した3件目の実例**として ⑤ の適用例に加える。

## 2. ①' 追加条文 — **PR 本文と commit message の両方**から外さないと止まらない

**fleet が本リポで実踏（2026-07-31・PR #205）。起草側の原文には無い。**

### 条文（① と同じ収載先・① の直後に置く）

> closing keyword による自動クローズを**止めたい**とき（＝観測してから手動で閉じたいとき）は、
> **PR 本文と commit message の両方**から keyword を外す（MUST）。
> squash マージでは**元コミットの message が merge commit の本文へそのまま取り込まれる**ため、
> PR 本文だけを直しても自動クローズは止まらない。

### 根拠（fleet 実測）

PR #205（#156 のフレーク修正）で、#156 自身が定めたクローズ条件「**マージ後の実 CI を複数回観測してから閉じる**」を守るため、hub 裁定 (a) に従って自動クローズを止める必要があった。PR 本文から `Closes` を外した時点では**まだ止まっていなかった** — commit message 側に残っていた。

**squash マージの本文に元コミットの message が入ることは本リポの履歴で実測できる**（`git log -1 --format=%b 27f5887`）:

```
* docs(daily): 2026-07-30 の日報（…）（#173）

  Co-Authored-By: …

* docs(daily): 2026-07-30 の日報に origin ゲート導入の未完遂を追記（#173）

  publish 完了後に hub 号令で origin 導入へ着手し、…
```

＝ ブランチ上の各コミットの本文が `* ` 付きで merge commit の本文へ連結される。ここに closing keyword があれば、**PR 本文をどう直しても merge commit の本文には残る**。

🔴 **未実測**: 「merge commit の本文にある keyword から実際に自動クローズが発火するか」は**試していない**。試すと #156 が閉じてしまい、#156 が定めた観測期間そのものが壊れるため。GitHub の公開仕様上は既定ブランチへ入ったコミットの message も closing keyword を解釈するので、**発火する前提で両方から外す**という予防的な扱いにしている。**この1点は推測を含む。**

### 実装の型（写せる形）

```bash
# PR 本文・commit message の両方を走査（0 件であることを主張する側）
gh pr view <N> --json body -q '.body' | grep -ciE '(clos(e|es|ed)|fix(es|ed)?|resolve(s|d)?) #<ISSUE>'
git log -1 --format='%B'             | grep -ciE '(clos(e|es|ed)|fix(es|ed)?|resolve(s|d)?) #<ISSUE>'
# 陽性対照（→ §3・検出器が生きていることの証明）
echo "Closes #<ISSUE>"               | grep -ciE '(clos(e|es|ed)|fix(es|ed)?|resolve(s|d)?) #<ISSUE>'
```

代わりに `Refs #NNN` を置き、**マージ後に手動クローズする手順を PR 本文に明記する**（PR #205 の形）。

## 3. ①'' 追加条文 — 「バッククォートで無効化できる」に**依存しない**

**fleet の観察と判断（2026-07-31・hub 承認済み）。①の裏面。**

### 条文（① と同じ収載先・① の直後に置く）

> closing keyword を**意図的に無効化したい**場合に、**バッククォートで囲う方法に依存してはならない**（MUST NOT）。
> 無効化したいなら **keyword と issue 番号の隣接そのものを文面から外す**。

### 根拠（依存が壊れる向きが最悪である）

① は「バッククォートで囲うと効かない」という事象である。裏返せば **「意図的に無効化する手段」としても使える**ように見える。実際 PR #205 の本文で、条文の説明として `` `Closes #156` `` と書いた箇所が自分の走査に引っかかった（① の判例に従えば発火しないはず）。

fleet はこれに**依存しなかった**。理由:

- 「効かないはず」に頼ると、**GitHub 側の挙動が変わった瞬間に静かに自動クローズされる**。
- しかも #156 のように「マージ後に観測してから閉じる」運用では、**観測期間中に閉じられると「観測が完了したように見える」**。これは ⑤「意味の違う正常値」の中でも**最悪の壊れ方**で、失敗が「成功の完了」の顔をして現れる。
- ① の主張（無言で閉じ残る）と ①'' の主張（無言で閉じる）は**同一の未定義動作への依存**であり、方向が違うだけ。片方を「バグ」と呼びながらもう片方を「手段」として使うのは一貫しない。

したがって条文化にあたり、**「バッククォートで無効化してよい」とは書かない**（hub 裁定 2026-07-31）。

## 4. 機械検査 — fleet は「足す」を推す（起草側は条文のみで足りると見ている）

起草側は「規約文言だけで足りる規模」と見ているが、**fleet としては軽量検査を足す方を推す**。理由は起草側自身が書いた「**丁寧な書き手ほど踏む**」で、規約文言は結局「気をつける」に帰着するため。#154 の ⑤ にはこう書いてある:

> この型は、**意識して対策している人が、その対策のコードの中で、もう一度踏む**。「気をつける」では防げないので、レビューで一度問うのが実効的。

🔴 **本 patch を書いている最中に、まさにそれが起きた** — ① を条文化する PR の本文で、fleet 自身が keyword を書いてしまった（§3）。**⑤ の「対策のコードの中でもう一度踏む」の4件目の実例**であり、条文だけでは足りないことの自己証明になっている。

### 検査の形（起草側提案 ＋ fleet の追加）

- 検出: **PR body に加えて commit message も**走査し（§2）、`` `(Closes|Fixes|Resolves)\s+#\d+` `` のバッククォート付き出現があれば警告。
- **警告に留める**（block しない）。closing keyword を意図的に無効化したい場面（related issue を挙げるだけ・観測後クローズ）があるため。ただし §3 のとおり**無効化の手段としてバッククォートを使わせない**ので、警告文には「無効化したいなら keyword と番号の隣接を外せ」と書く。
- 実装は GitHub Actions 数行。コストがほぼゼロなので、条文＋検査の二段が妥当。

**未確定**: 実装は本 patch のスコープ外（条文の文面凍結まで）。検査器の実装は別 issue で。
