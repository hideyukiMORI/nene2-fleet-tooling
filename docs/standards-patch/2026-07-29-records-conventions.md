## 1. ① CSP は「必要な指令を・必要なページだけ」広げる。nonce は使う場面でだけ生成する

### 条文（`02 §9.6` 新設・冒頭条文）

> CSP を緩めるときは、**緩める指令を最小に、緩める応答面も最小に**する（MUST）。
> 機能Aのために `script-src` が要るなら `script-src` だけを足し、無関係な指令（`img-src`・`connect-src` 等）は触らない。HTML 応答が困っていても API 応答の CSP は巻き込まない。
>
> **nonce は「その応答が実際に nonce 付き `<script>` を出すとき」にだけ生成**し（MUST）、出さない応答の CSP は従来と**バイト単位で同一**に保つ（→ ②が機械で固定する）。
>
> 「とりあえず全ページで nonce を出す」「まとめて `'unsafe-inline'` にする」は MUST NOT。前者は nonce の意味（この応答が意図した1本だけを許可する）を薄め、後者は**その指令に対する CSP の防御を丸ごと捨てる**。

### 根拠（records 実測の要点）

- 出発点（records #555 → #557 / PR #558）: `default-src 'self'` が公開SPAの inline `<style>`・`data:` フォントをブロック。**本番実機で初めて発現**（dev は Vite 経由で隠れていた — ③の現物）。**違反 56 件は `/posts/246` という単一ページの数**であり、サイト全体の合計ではない（出典＝実機検証レポート #555・#557 はその修正 issue）。ここで `style-src`/`font-src`/`img-src` だけを緩め **`script-src` は `'self'` のまま**・公開HTML応答にだけ付与。
- nonce 機構の導入（GA4・PR #583）: 分析タグの inline `<script>` に nonce を付け `script-src` に `'nonce-…'` と GTM ホストを追加。このとき**分析が無効な org では nonce を一切生成しない**設計にしたため、当該 org の CSP は既定定数と**バイト単位で同一**のまま保たれた。以降の分岐（#982）はこの機構の拡張である。
- 分岐点（records #982 / PR #995）: 分析と無関係な極小 inline script の需要が発生。「分析も一緒に有効化」「`'unsafe-inline'` を足す」のどちらにも倒れず、**nonce の生成条件を「実際に script を描く応答」に絞り、組み立て側は「nonce があれば script-src にだけ付ける」**へ拡張。**対象外ページの CSP は1バイトも変わらない。**
- 同型の再演（records #802 / PR #803）: embed allowlist は `script-src`/`connect-src`/`frame-src` の3指令にだけ追加・allowlist 空なら出力は従来と byte-for-byte 同一（→②）。

### 実装の型（写せる形・records 実装より）

**生成と組み立ては別のファイル**である（この分離が①の要）。生成側は各レンダラ（`RenderPublicRecordViewHandler.php:129` / `RenderPublicTypeArchiveRenderer.php:54`）、組み立て側が `PublicHtmlCsp`（`:59-60`）。

```php
// 生成側（各レンダラ）: この応答が実際に nonce 付き <script> を出すときだけ生成する
$nonce = ($analytics->isEnabled() || $fabNeedsScript) ? bin2hex(random_bytes(16)) : '';

// 組み立て側（PublicHtmlCsp）: 無効なら既定定数をそのまま返す（= byte-for-byte 同一）
if (!$analytics->isEnabled() && !$hasNonce) {
    return self::POLICY;
}
```

### 届け先（起草側の明示要求 — mori-site ⑥の適用）

①を「CSP を書く章」にだけ置くと **CSP を書く人しか読まない**。実際に判断を誤るのは**機能を足す人**（分析・CTA・埋め込みの実装者）。よって `05 §6` の「機能追加時のチェックリスト」（contact ②' 枠）に**「外部/インラインスクリプトを足すときは ① を読む」の1行を必ず併載**する（W0b 収載時の指定・相互参照 MUST）。

## 2. ② CSP 出力を変える変更は「機能無効時の出力 byte-for-byte 同一」を回帰で pin する

### 条文（`02 §9.6`）

> CSP の組み立てに分岐を足す変更（新指令・新オリジン・nonce 条件の変更）では、**その機能を使っていない場合の出力が変更前と完全に一致する**ことをテストで固定する（MUST）。「だいたい同じ」「必要な指令は入っている」では不足で、**文字列として同一**（`assertSame` 相当）を assert する。
>
> 理由: CSP は**壊れても機能が動いてしまう**。緩めすぎの間違いは症状が出ず、**攻撃面だけが静かに広がる**。テストが落ちる方向に倒しておかない限り、最後の砦が CSP 文字列の目視 diff になる（指令が5つを超えたあたりで人間の精度は落ちる — records 起草者の実感値）。
>
> 厳格側の性質も pin してよい（SHOULD）: 例「`style-src` より前に `'unsafe-inline'` が現れない」＝「必要な指令にだけ付いている」を位置関係で機械化した形（records `PublicHtmlCspTest.php:70`）。

### 根拠

records #802 / #982 はどちらも**全公開ページが通る関数**への分岐追加。ただし**担保の置き場所が違う**（どちらも有効な型なので分けて記す）:

| 変更 | 担保 |
|---|---|
| #802 / PR #803（embed allowlist） | **コミット本文に受入条件として明記**（`d4eaa33`「空 allowlist なら現行と byte-for-byte 同一」）＋ `assertSame(PublicHtmlCsp::POLICY, $csp)`（`PublicHtmlCspTest.php:18`） |
| #982 / PR #995（CTA nonce・`ab0de01`） | **テストで pin**（`testDisabledAnalyticsWithoutNonceReturnsStrictBaseline` / `testNonceWithoutAnalyticsWidensOnlyScriptSrc`）。コミット本文に byte-for-byte の文言は無い |

条文が MUST として要求するのは**テストによる固定**であり、コミット本文への明記は SHOULD（レビュー時の合意を残す形）。

### 検査器の方向（hub 申し送り(b) の裁定を反映）

起草側の提案は2案（「全フラグ OFF == 既定定数」テストの存在検査／既定ポリシー定数の台帳化）。**採るのは後者=台帳化を優先**（hub 申し送り(b): テスト存在の静的判定は困難）。各製品の `PublicHtmlCsp::POLICY` 相当を registries に台帳化すれば、フリート横断で「どの製品がどこまで緩めているか」が一覧になり、差分＝レビュー対象になる。**registries への kind 追加は新検査器に接続するため凍結明けの patch 波**（§7）。

## 3. ③ CSP は本番でしか壊れない。dev の緑を「動いた」の根拠にしない

### 条文（`02 §9.6`）

> CSP に関わる変更の検証は、**本番と同じ CSP ヘッダの下で、実ブラウザ**で行う（MUST）。dev サーバは CSP が無い/緩いことが多く、**dev で動くことは何の証拠にもならない**。ユニットテストが証明できるのは「意図した文字列を出した」ことまでで、**その文字列の下でスクリプトが実際に走るか**は別問題。
>
> 検証は「コンソールに CSP 違反が出ないこと」の確認までを含める（MUST）。CSP 違反は**例外を投げず**、機能が静かに無効化されるだけなので、**症状を探しに行かないと見つからない**。
>
> 「実ブラウザ」は本番環境そのものである必要はない。**本番相当の CSP ヘッダを再現したヘッドレスブラウザで足りる**（records #857 の実施形）。本番を持たない段階の製品でも守れる。

### 根拠

- records #555 / #557 の違反は**本番の単一オリジン実機検証で初めて**出た（`/posts/246` 単一ページで 56 件）。それまでの開発とテストは全部緑で、dev は Vite 経由のため CSP が効いておらず露見しなかった。
- records #857（④）は**本番相当 CSP を再現したヘッドレス Chromium** で初めて `SCRIPT_BLOCKED` を捕捉。

### 一般則への昇格（hub 申し送り(c)・fleet 判断）

③は CSP 固有ではない。07-29 にフリートで確認された「ゲート実行の緑を判定材料にしない」（serve の brace-expansion）・「検査しない対象の green」（G-6・#164）と**同じ型** — 「**緑は『壊れていない証明』ではなく『そのコードパスを通っていないだけ』かもしれない**」。fleet 判断: **一般則としては `06-testing-verification.md`（方向承認済み・凍結明け）の柱の1本に送り**、本条は CSP 文脈の適用形として `02 §9.6` に置く（一般則と適用形の両置き・相互参照）。⑤の締め文「**叩かれていないメソッドは、動いていないのではなく、確かめていないだけ**」も同じ柱に併載する。

## 4. ④ `srcdoc` の iframe は親ページの CSP を継承する。sandbox は CSP の代わりにならない

### 条文（`02 §9.6`）

> `<iframe sandbox="allow-scripts" srcdoc="...">` に任意の HTML/JS を流し込む設計を、「隔離したので安全に実行できる」根拠で採ってはならない（MUST NOT）。`srcdoc` の iframe には**親ページの CSP がそのまま適用される**（ブラウザ仕様）。`sandbox` は DOM/オリジンの隔離であって、**CSP の適用範囲を切り替えるものではない**。
>
> 帰結は親ページの CSP によって2通りに分かれるが、**どちらでもこの設計は成立しない**:
> - 親 CSP が inline/外部 script を許していない（＝あるべき状態）→ **安全になるのではなく、動かなくなる**。
> - 親 CSP に `'unsafe-inline'` 等があり**動いてしまう** → それは親ページ側の CSP が緩いということであって、**隔離が成立している証拠ではない**。「うちは動くから当てはまらない」は誤読。
>
> 任意 JS を伴うコンテンツを配信するなら、**別オリジンに実 URL で置き `src=` で読む**（SHOULD）。CSP はオリジン単位で当てられるので、そこで初めて「そのコンテンツ用の CSP」を設計できる。**ただし別オリジン実 URL 配信は配信基盤（オリジン・デプロイ経路・キャッシュ）を1式持つコストを伴う**（records #857 の LP 配信モデル参照 — hub 申し送り(a)）。コストを払えない場合の答えは「では srcdoc で」**ではなく**「任意 JS 実行という要件自体を落とす」。
>
> 🔴 **参照実装はフリート内にまだ存在しない**（2026-07-29 時点）: records #857 は **OPEN**・LP バンドル PoC も**未着手**。本 SHOULD を採る艦は手本を探しに行かず、自艦で設計することになる。

**この MUST NOT が禁じる射程**: 「隔離したから安全に動く」という**理由づけ**であって、`srcdoc` + `sandbox` の使用そのものではない。script を伴わない untrusted HTML の表示に使うことは禁じていない（records も bundle 以外で srcdoc を全廃していない）。

### 根拠

records #311 の `SandboxedBundle.tsx` は "scripts execute but cannot reach the parent DOM" とコメントしていたが、**実際には scripts execute しない**（`script-src` が `default-src 'self'` から継承され inline script は実行拒否）。**設計前提そのものが偽**。現在は単発パッチで潰さず別オリジン配信モデル（#857）へ統合して解く方針 — **間違った前提のまま小さく直さない**判断も教訓として併記する。「ユーザ提供 HTML を安全に表示する」要求はどの製品にも出るし、`srcdoc`+`sandbox` は**一番手軽に見えるが要件を満たさない**ので、条文で先回りして潰す価値がある。

## 5. ⑤ 読み取りに能力を要求するときは、GET と HEAD を必ず同じ扱いにする

### 条文（暫定 `02 §3` 追補「認可解決」）

> 認可（どの操作にどの権限が要るか）をパスとメソッドから解決するとき、**読み取りメソッドを単一の等値比較で書かない**（MUST NOT）。`$method === 'GET'` は **HEAD を認可段から抜け落とし**、同じリソースへの認可がメソッドで効いたり効かなかったりする状態を作る。
>
> 読み取りは**両メソッドを明示的に列挙**する（MUST）。次のいずれかの形をとる:
>
> 1. `match ($method) { 'GET', 'HEAD' => Capability::…, … }`（列挙）
> 2. `$method === 'GET' || $method === 'HEAD'`（論理和）
> 3. 読み取り述語を1つ定義し、全分岐がそれを使う
>
> 禁じているのは**読み取りメソッドの片方だけを見る**ことであって、特定の構文ではない。
>
> HEAD は本文を返さないので「漏れない」と考えたくなるが、**ステータスコードは返る**。`404` と `200` の差はそのまま**リソースの存在オラクル**であり、`Content-Length` が付く構成なら**規模の推定**まで通る。

### 根拠

- records #1023: `CapabilityResolver::resolve()`（`:98`）の1分岐だけが `$method === 'GET'` で、認証済み低権限ユーザの HEAD が認可段を素通り（`null` = 能力不要と解釈）。**全分岐を GET/HEAD で突き合わせた実測で、「両メソッドを明示しているか」がそのまま健全性の判別条件だった**:

  | 書き方 | 分岐 | 結果 |
  |---|---|---|
  | `match ($method) { 'GET', 'HEAD' => … }` | settings（`:43-47`）／navigation-items（`:51-55`）／widgets（`:59-63`） | 🟢 無事 |
  | `match (true)` ＋ 論理和 | media（`:85-89`） | 🟢 無事 |
  | `$method === 'GET'`（単一等値） | users の読み（`:98`） | 🔴 素通り |

  **健全な分岐は同一構文ではない**（列挙3・論理和1）。共通しているのは「両メソッドを明示していること」だけで、これが条文の許容形を構文で縛らない理由。変更系（`isMutationMethod()`・`:118`）は全部健全＝壊れるのは「読みに権限を要求する」側だけ。
- レビューで見つけにくい理由: `$method === 'GET'` は読んで違和感がなく、**正しい分岐のすぐ隣**でも起きる。HEAD を叩くテストを書く習慣も無い。
- 横断（統合リナ grep・2026-07-29／records が行番号の実在を再確認）: **単一等値**が concierge 2箇所（`CapabilityResolver.php:34,39`）・payout 1箇所（同 `:58`）。**論理和で正しく書けていた**のが profile（`:44`）・vault（`:55`）。🔴 **横断ぶんは grep 一致のみで周辺ロジック未読** — 現時点で言えるのは「同じ書き方が3箇所ある」までであり、**バグと断定しない**（hub 申し送り・各艦の実測待ち）。

### 検査器の方向

起草側の2案のうち、fleet の見立ては**案2（代表パス × {GET, HEAD} のテーブル駆動テストを各製品に配る）優先**。案1（`=== 'GET'` の静的検出）は誤検知抑制の理由コメント規約まで含めると重く、案2は records で実際に3パスの不一致を即座に出した実績がある。いずれも**新検査器 = 凍結明け**（§7）。
